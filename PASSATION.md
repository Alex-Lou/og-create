# Passation — Brumelune

Document pour l'agent qui reprend le projet : ce qu'est le jeu, comment travailler avec son auteur, comment le code est
construit, ce qui est fait et ce qui reste à faire. **À lire en entier avant la première ligne de code.**
L'histoire, les personnages et le game design sont dans **`HISTOIRE.md`** (la bible, à lire ensuite).
État au 5 octobre 2026, après les lots H0 à H3 de la bible (la troupe et les textes ; la colonne vertébrale ; le fil d'Ariane ; dormeurs, naufrages et souvenirs).

## 1. Le projet en bref

Jeu d'alchimie en français, sur mobile d'abord (PWA installable) :

- **le Grimoire** (*Codex Mundi* ; « le Livre » dans le code) : on découvre des centaines d'éléments en les mélangeant dans l'Athanor ; pages, chapitres, énigmes,
  encre, pendu des lettres ;
- **l'Épreuve** : questions chronométrées ;
- **l'Île** (le Monde) : une île isométrique de 96 × 96 cases. On y bâtit 7 bâtiments à 7 paliers, on achète des
  quartiers, on joue la Récolte (un jeu d'alignement) pour gagner des ressources, et on y retrouve des habitants, des
  visiteurs, des annexes, des créations d'île, des coffres, des mini-jeux, des expéditions, des lieux remarquables et
  des trouvailles de climat.

| Dépôt | Rôle | Branche par défaut | Local (sessions cloud) |
|---|---|---|---|
| `Alex-Lou/og-create` | front Vue 3 (Options API, Vite, aucune librairie de jeu) | `master` | `/home/user/og-create` |
| `Alex-Lou/Og-create-backend` | API Express + PostgreSQL | `main` | `/home/user/og-create-backend` |

- **Déploiement** : Render (front statique, API) et Neon (Postgres). Voir `DEPLOY.md`.
  - Le build Render de l'API lance `npm run db:setup` : schéma et contenu, rejouable, sans toucher aux comptes.
- **Taille** : environ 30 700 lignes côté front, 6 300 côté serveur.
- **Le serveur fait autorité sur tout** : recettes, écus, ressources, île, coffres. Le navigateur n'affiche que des
  résultats ; il ne décide jamais d'un gain.

## 2. Travailler avec l'auteur (à respecter strictement)

### Préférences
- Répondre **en français**, en mode expert : DRY, KISS, SOLID, YAGNI.
- **« Demandez, ne supposez pas »** : poser la question avant de coder dès qu'un choix structurant n'est pas tranché.
  L'outil de questions à choix (2 à 4 options, la recommandée en premier avec « (Recommandé) ») marche très bien avec
  lui ; il choisit presque toujours la recommandation, à condition qu'elle soit bien argumentée.
- Ne **jamais** toucher au code sans rapport avec la tâche : signaler l'amélioration à la fin, sans la faire.
- Signaler toute incertitude. Ne jamais affirmer un résultat qu'on n'a pas vérifié, et dire ce qui n'a pas été mesuré.
- Confirmer avant toute suppression, tout remplacement de code existant ou toute action irréversible.
- Ne rien envoyer, publier ni partager en son nom sans confirmation dans le message courant.
- Finir chaque tâche de code par :
  **Fichiers modifiés / Ce qui a été modifié / Fichiers intentionnellement non touchés / Suivi nécessaire.**

### Sécurité et procédure
- Ne jamais coller ni demander de clé d'API.
- **Jamais `pkill -f`.** Tuer un processus par son PID, par exemple le serveur local :
  `for p in $(pgrep -x node); do if tr '\0' ' ' < /proc/$p/cmdline | grep -q "src/server.js"; then kill $p; fi; done`
- Ne pas lire d'identifiants dans l'environnement des processus. N'utiliser que des comptes de test créés soi-même.
- **`git reset --hard` : jamais sans être certain d'avoir une copie** de ce qui risque d'être perdu.

### Git, PR et fusion
- Travailler sur la branche de session indiquée par l'environnement (jusqu'ici `ccr-02f8926c-2j3n3t` dans les deux
  dépôts). Ouvrir les PR **en brouillon** et s'y abonner.
- **Accord permanent de fusion sur CI verte**, dans cet ordre :
  1. passer la PR en « prête » (draft: false) ;
  2. fusionner en squash, avec le SHA complet (40 caractères) de la tête en `expectedHeadSha` ;
  3. **le serveur d'abord, puis le front juste derrière** : un ancien front casse souvent face à une nouvelle API.
- Après une fusion :
  1. vérifier que le diff entre l'ancienne tête et `origin/<défaut>` est vide ;
  2. `git checkout -B <branche> origin/<défaut>` ;
  3. `git push --force-with-lease=<branche>:<ancien sha> origin <branche>` ;
  4. se désabonner de la PR.
- Attribution des commits, en fin de message :
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` et `Claude-Session: <URL de la session en cours>`.
- Les descriptions de PR se terminent par `🤖 Generated with [Claude Code](https://claude.com/claude-code)`, l'URL de
  session, puis `---` et `_Generated by [Claude Code](https://claude.ai/code)_`.
- **Aucun identifiant de modèle** dans les commits, les PR ni le code.
- **CI front** : `npm run lint`, `npm test`, `npm run build`.
- **CI serveur** : Postgres 16, `npm run db:setup`, `npm test`.

### Style de livraison
- Découper en **lots** (9a, 9b…), chacun livré en une paire de PR (serveur puis front) avec ses tests.
- Pour les gros lots, livrer en deux temps (par exemple 9d-1 puis 9d-2).
- Vérifier visuellement chaque dessin (planche SVG → PNG) et chaque parcours dans un vrai navigateur (§ 4).

## 4. Vérifier dans un navigateur

Chromium est préinstallé : Playwright le trouve via `PLAYWRIGHT_BROWSERS_PATH`. Ne pas lancer `playwright install`.

Les scripts de vérification de bout en bout vivaient dans le dossier temporaire de la session : ils sont perdus.
La recette pour les refaire :

1. Ouvrir `http://localhost:8080/` en viewport mobile.
2. Créer un compte de test : `POST /api/auth/register` avec les en-têtes `Content-Type: application/json` et
   `X-Requested-With: origins`.
3. Mettre dans `localStorage` :
   - `user` ;
   - `oc_guide_seen` (les répliques de Brume déjà vues) ;
   - `oc_brume_born=1`.
4. Préparer l'état en SQL (`psql $DATABASE_URL`), par exemple :
   - `INSERT INTO progress (user_id, infinite_elements, coins) …` : éléments du Livre et écus ;
   - `world_zones` : quartiers à soi ;
   - `world_expeditions` avec `ends_at` passé : quartiers découverts ;
   - `world_buildings`, `world_finds`, `world_crafts`, puis `UPDATE world_stock SET stone = … …`.
5. Recharger `/?heure=jour&meteo=clair` (ou `heure=nuit`), toucher le bouton « Île ».
6. Piloter l'île depuis la page avec `const v = document.querySelector('.world').__vueParentComponent.proxy`, par
   exemple :
   - `v.cam.x / v.cam.y / v.cam.s` puis `v.clampCam(); v.draw(performance.now())` ;
   - `v.ground(x, y)` donne le point du monde d'une case, `v.toScreen(...)` le point écran (pour simuler un toucher) ;
   - `v.tipOf({...})`, `v.startCraftPlace(id)`, `v.benchOpen = true`.
7. Capturer `.world__stage` et assembler les captures en planches pour les regarder.

**Mesure du temps de dessin** : dans la page, appeler `v.draw()` 30 fois (pour préparer les carrés de sol), puis
chronométrer 20 appels. Comparer à zoom égal, au même endroit.

## 5. Architecture

### Principes
- **Serveur seul juge** : chaque action passe par une transaction qui verrouille la ligne `world_stock` du joueur
  (`stockOf(userId, conn, true)`). Un double clic ne paie donc jamais deux fois ; les tests le vérifient (deux appels
  en parallèle → un 200 et un 409).
- **Une seule vue** : `GET /play/world` renvoie tout l'état de l'île. Chaque action renvoie `{ …, world }` et le front
  fait `apply(world)`.
- **Migration paresseuse** de la carte (`migrate(userId)`, v1 → v2 → v3 → v4), verrouillée, au premier passage du
  joueur. Pour décaler des cases sans conflit de clé unique, on décale en deux temps (+1000, puis −1000 + décalage).
- **Fonctions pures séparées de la base** : `worldMap`, `crafts`, `annexes`, `landmarks`, `finds`, `loot`,
  `villagers`, `visitors`, `minigames`, `harvest` sont pures et testées sans base. `world.js` fait les transactions et
  la vue.
- **Conventions de code** : commentaires en français, denses et explicatifs, au-dessus de chaque fonction. Noms
  courts. Pas de nouvelle dépendance sans en parler. Front en Options API. Chaque fichier a un en-tête qui dit ce
  qu'il contient.

### Styles du front : `src/styles/` (refonte CSS, octobre 2026)
- **Trois étages** (détail et règles : `src/styles/README.md`) : les **jetons** (`styles/tokens/`, un fichier par famille :
  couleurs, typographie, formes et ombres, rôles `--oc-*`, mouvement, mise en page, thème sombre en dernier), la
  **base** (`styles/base/` : remise à zéro et primitives `g-*`, dans un ordre qui compte), puis le **style de chaque
  composant**, à côté de lui. `main.js` n'importe que `styles/index.css`.
- **Refonte en cours, par petites PR, sans rien changer à l'écran** (choix de l'auteur : un dossier par composant,
  `.vue` et `.css` côte à côte ; des jetons pour les couleurs, la typographie, les formes et la profondeur ; les
  marges, tailles et durées restent des nombres) : 1) jetons et base découpés (fait) ; 2) chaque composant de l'île reprend ses styles (fait :
  `X.css` à côté de chaque composant, en `<style scoped src>` ; les primitives partagées des fiches de l'île dans
  `components/World/island-ui.css`, global, chargé par `WorldView`) ; 3) les valeurs en dur deviennent des jetons,
  sur trois niveaux (la palette ; des rôles globaux pour ce que plusieurs composants partagent ; des jetons locaux
  nommés en tête du CSS de chaque composant) : 3a-1 formes, profondeurs (`tokens/depth.css`, l'ordre des couches),
  police IM Fell et durées (fait), 3a-2 couleurs partagées (fait : succès, manque, or vif, halo des illustrations,
  pièce d'or, `--gold-100`, et `--shade-rgb` pour le brun des liserés à toute transparence), 3b-1 l'île (fait :
  `tokens/island.css` pour ce que ses composants partagent, adopté partout ; `--oc-gold-ink`, `--oc-night-ink` ;
  jetons locaux du décor de l'île, en tête de chaque CSS, sur la racine du composant), 3b-2 les fiches et les
  mini-jeux de l'île (fait : plus aucune valeur en dur dans `components/World`, hors noir et blanc), 3c-1 les teintes
  partagées entre domaines (fait : canaux `-rgb` de l'or et de l'encre, `--oc-aim`, `--oc-glow-*`, `--oc-gilt-rgb` ;
  `tests/tokens.test.js`), puis les jetons locaux du Grimoire et du reste ;
  4) les dossiers rangés par domaine ; 5) `App.vue` et `BookView.vue` découpés.
- **Piège du passage en scoped** : une règle scoped gagne un attribut de spécificité. Si elle vise aussi la racine d'un
  composant enfant (un glyphe `img.glyph` dans un portrait, par exemple), elle peut l'emporter sur le style propre de
  l'enfant : garder la spécificité d'avant avec `:where()` sur l'ancêtre (`SiteOverview.css`, le portrait).
- **Preuve « rien de cassé »** pour chaque étape : le CSS compilé comparé avant/après (mêmes règles dans le même
  ordre ; quand des valeurs deviennent des jetons, chaque `var()` remplacé par sa valeur, en clair puis en Veillée,
  doit redonner la valeur d'avant) et un banc de captures (23 écrans, sur téléphone, PC et téléphone en Veillée, même
  compte, horloges de la page figées) comparé pixel par pixel ; en plus du lint, des tests et du build.
- **Banc** : les délais que le serveur calcule à son heure réelle (« encore 23 h » dans la fiche d'un habitant)
  sont neutralisés à la capture ; refaire la référence sur master quand le compte du banc a vieilli.
- **Jeton et Veillée** : une valeur en dur ne devient un jeton de la palette que si ce jeton garde la même valeur en
  Veillée (`tokens/dark.css` redéfinit les vélins : un `#fffcf5` écrit en dur n'est pas `--vellum-50`).

### Serveur : `src/services/`
- **Carte**
  - `worldMap.js` : la très grande île 96 × 96. Elle assemble `islandData.js` (le cœur, ancienne carte 48 × 48
    posée en `OFFSET`) et `islandOuter.js` (les terres nouvelles). On y trouve :
    - les 24 quartiers et leurs climats ;
    - les voisinages, les ancres de panneau ;
    - le masquage des quartiers inconnus.
  - `worldMapV2.js` : l'ancienne carte, gardée pour la migration.
- **Le jeu de l'île**
  - `world.js` : l'API de l'île (≈ 650 lignes) : la vue, les quêtes, les chantiers, la Récolte, les mini-jeux, la
    boutique, les noms. Le reste est découpé par domaine dans `world/` (lot « santé ») ; `world.js` réexporte tout,
    avec la même API. Dépendances, sans cycle, dans cet ordre :
    - `rules.js` : constantes, chantiers (`SITES`), effets, production, charges (rien en base) ;
    - `reads.js` : lectures de l'état d'un joueur en base ;
    - `migrate.js` : passage des cartes v1 → v4 ;
    - `chests.js` : les coffres (vue et ouverture) ;
    - `people.js` : habitants (présence, humeurs, besoins, amitié), visiteurs ; il appelle `produce.gatherBefore`
      seulement à l'exécution (`require` différé : `produce.js` lit déjà `people.js`) ;
    - `produce.js` : bonus et récolte de la production ;
    - `anyaBrume.js` : Anya (éveil, Révélation, Souffle) et le Savoir de Brume ;
    - `lands.js` : expéditions, lieux remarquables, gisements ;
    - `creations.js` : créations d'île (pose, établi, assemblage) ;
    - `annexPlots.js` : annexes posées (cases permises, pose, déplacement).
  - Les bonus se combinent dans cet ordre :
    1. `shop.bonusesOf` (boutique) ;
    2. `annexes.bonusesOf` ;
    3. `withMoods` (humeur des habitants) ;
    4. `withLandmarks` (lieux remarquables).

    Le résultat est lu par `effectsOf` (réserve de parties, coups, retour des parties) et `productionAll`.
  - **Production juste** : chaque heure produite compte avec l'humeur de son moment.
    - L'humeur change d'elle-même quand un besoin arrive à échéance. `prodSteps` (`people.js`) donne la part en plus
      de chaque bâtiment à chaque échéance depuis la dernière récolte ; `productionAll` s'en sert, pour la vue comme
      pour le ramassage.
    - Quand le joueur change une humeur (besoin comblé, création posée, déplacée ou rangée, visiteur installé),
      `gatherBefore` (`produce.js`) encaisse d'abord la production, si la part d'un bâtiment en change sur la
      fenêtre. La réponse porte alors `coins` (le solde), que le front transmet.
    - Encore comptées à l'instant du ramassage : la Bénédiction d'Anya et la fin du prologue (une seule fois dans une
      partie, sur une seule récolte).

### Front : `src/world/` (moteur de l'île) et `src/components/World/`
- **`WorldView.vue`** : l'île entière (≈ 2 740 lignes : ≈ 370 de gabarit, ≈ 2 000 de script, ≈ 350 de styles) : son
  état, le chargement, les actions ; elle assemble les fiches et le HUD, qui sont des composants.
  Ses méthodes de moteur sont à part, dans `src/world/view/`, des objets de méthodes étalés dans `methods`
  (`this` y reste le composant) :
  - `camera.js` : géométrie isométrique (monde ↔ écran), caméra, zoom, cadrage ;
  - `draw.js` : la boucle et le dessin (sol, mer, tri par profondeur de ce qui se tient debout, lumières, météo,
    bulles) ;
  - `gestures.js` : glisser, pincer, molette, toucher, appui long, ce qui est sous le doigt ;
  - `constants.js` (taille d'une case…) et `memory.js` (la vue gardée d'une visite à l'autre de l'onglet).
  - Fiches et HUD en composants : le naufrage (`WreckScene`), Brume (`BrumeSheet`), un quartier (`ZoneSheet`), un
    bâtiment (`SiteSheet` : en-tête et onglets ; l'onglet ouvert vient en slot de l'île : `SiteOverview`, `SiteShop`,
    `AnnexPanel`, `SiteSteps`) ; la barre du haut (`IslandHud`, dans `.world__top` que l'île mesure) et les boutons
    posés sur l'île (`IslandButtons`). Leurs styles restent dans `WorldView` (globaux, classes `world__`) ; les actions
    restent à l'île, qui les reçoit en événements. Les règles de la boutique et des paliers (verrous, prix, palier
    prêt) sont dans `src/world/shop.js` et `src/world/levels.js`, testées.
- **Le sol** : `terrain.js` (`TerrainCache`) peint le relief en **carrés de 512 px gardés en images**, à des
  résolutions par pas de √2.
  - Le décor fixe (arbres, rochers) est **cuit dans le sol** sauf de près : `NEAR_SCALE = 0.9`, avec le vent
    seulement de près.
  - Clé d'un carré : `${res}${bake ? 'b' : ''}:${tx},${ty}`.
  - Le décor proche de ce qui se tient debout (`liveCellsOf`) n'est jamais cuit, pour pouvoir passer devant.
  - Ce qui marche (habitants, bêtes) passe partout : au zoom moyen, le décor cuit des cases devant lui qui le
    recouvre est repeint par-dessus, dans sa boîte seulement (`standInFront`, `drawSpriteIn`) ; ≈ 0,8 ms par image
    pour une vingtaine de bêtes, mesuré en rendu logiciel.
  - `occlude()` repeint les cases de relief devant un objet, ainsi que leur décor cuit.
- **Les dessins** sont des SVG **générés par le code** (repère isométrique `iso.js` : `P(u, v, z)`, `box`,
  `gable`, `boulder` ; outils `tools()` de `shopSprites.js`). Ils sont rastérisés et mis en cache par
  `spriteCache.js` (`drawSprite`), avec des versions réduites selon le zoom (`setSpriteDetail`).
- **Modules de dessins** : `sprites.js`, `buildings2.js`, `looks.js` (bâtiments) ; `nature.js` (décor) ;
  `annexSprites.js`, `craftSprites.js`, `landmarkSprites.js`, `depositSprites.js`, `shopSprites.js`,
  `rareSprites.js`, `isletSprites.js`, `seaSprites.js`, `villagers.js` (générateur de personnages), `animals.js`.
- **Format d'un dessin** : un objet `{ layers: [{ frame: [x, y, w, h], n, fps, draw(T, f, n) }], light?() }`.
  Une animation, ce sont n images jouées à `fps`.
  - Pour en ajouter un : l'écrire dans le module, l'exporter dans le catalogue, le tester (pas de `NaN`, plusieurs
    images) et le **regarder** en planche PNG.
- **Ambiance** : `scene.js` (ciel, météo, `glow`), `sky.js`, `sea.js` (mer vivante), `climates.js` (teinte et
  particules de chaque climat), `brume.js` (Brume, le guide).
- **Fonctions d'affichage** : `landmarks.js`, `finds.js`, `annexes.js`, `crafts.js`, `chest.js`, `needs.js`,
  `friends.js` (pures, testées).
- **Fenêtres** : `GModal` (ui) porte `CraftBench`, `CraftPuzzle`, `AnnexPanel`, `ChestList`, `ChestReveal`,
  `ExplorerLog` (Carnet), `FindsSheet` (réserve de trouvailles), `VillagerSheet`, `VisitorSheet`…
- **Icônes** : `src/utils/icons.js`, désignées par `ui:<nom>` (ressources, trouvailles…). Les éléments du Livre
  sont des `svg:<nom>` dans `public/icons/elements/`.
- **Brume** : `src/game/guide.js` et `guideTips.js`, des répliques dites une seule fois, retenues sur l'appareil.

     fois par question (`coin_ledger`, `timer-question`). Risque faible : le palier I s'ouvre aussi à 10 découvertes,
     et rien ne se gagne en écus. Compter plutôt les questions payées ferait reculer un joueur dont les réussites ne sont
     pas toutes au grand livre (réussies en invité : seul un compte est payé) : à décider avec l'auteur.
   - ~~**L'Encre** achetée n'est retenue que sur l'appareil~~ : corrigé (chaque usage est inscrit au grand livre,
     référence : la page ; `/play/book` renvoie `ink` ; une page ne se repaie pas). Les achats d'avant, sans page au
     grand livre, restent retrouvés par l'appareil (`oc_book_ink`).
   - **Recharge des parties de Récolte** : comptée avec l'humeur de Cannelle (et la boutique, le Four, le Col) **à
     l'instant du calcul**, comme la production avant la correction de l'humeur. Écart faible (±3 min sur 30). Pour
     la rendre juste : arrêter les compteurs (`charges`, `charges_at`) avant chaque changement de recharge (combler
     un besoin, créations, visiteur installé, Cuisine ou Sablier, Four, Col du Vent), et compter par morceaux entre
     les échéances des besoins, comme `prodSteps`.
   - ~~**Courses** (double clic, deux onglets) sur les écus, les ressources et les récompenses~~ : auditées route par
     route. Quatre défauts corrigés :
     - un article de la Récolte (coups, réserve, recharge) se rendait après avoir servi à une partie ou à une
       expédition ; il ne se rend plus ;
     - un skin porté pendant que son achat s'annulait restait porté ;
     - deux recalculs des succès s'écrasaient ;
     - une création déplacée pendant l'ouverture de l'île pouvait être rangée à tort.

     Reste, sans enjeu d'écus : une Épreuve jouée dans deux onglets peut perdre une réussite de la liste du niveau
     (`trial.start`). Les points restent payés une fois, et seul le joueur y perd.
   - **`DECO_PRICES`** et la table `world_tiles` (`world.js`) : à garder tant que des joueurs peuvent avoir
     d'anciennes décorations à rembourser. Toute suppression en base attend **le feu vert explicite** de l'auteur.

## 8. Pièges connus

- **Tests serveur et limites de requêtes** : toutes les requêtes d'un fichier de tests viennent de 127.0.0.1, dans un
  même serveur. La limite de jeu par adresse (600 par minute) est relevée pour eux par `PLAY_ADDRESS_RATE_LIMIT`
  (`test/helpers.js`) ; un 429 « Doucement ! » dans un test qui passe seul vient de là.
- **Tester une course** : `whileHeld(hold, request)` (`test/helpers.js`) la rejoue à coup sûr. Une transaction du test
  fait ses écritures et garde ses verrous ; la requête part ; la transaction est validée dès que la requête attend
  l'un de ses verrous.
- **Changer une version des outils du front** (Vite, Vitest) : `npm install` de npm 10 (Node 22) s'arrête sur
  « Cannot read properties of null (reading 'edgesOut') », un bug de npm. `npx npm@11 install` passe ; le lockfile
  obtenu s'installe ensuite normalement avec npm 10 (`npm ci`, comme la CI).
- **Coordonnées** : la carte v4 décale le cœur de `OFFSET = (34, 26)`. Les tests utilisent `X(x)` et `Y(y)` pour
  écrire des coordonnées du cœur.
- **Quartiers inconnus** : la vue envoie leur relief et leur sol masqués (`'1'` et `'u'`), sans nom ni climat. Leurs
  lieux remarquables ne disent que leur existence (`{ id, zone, known: false }`, sans case) et leurs gisements ne sont
  pas envoyés.
- **Rien ne se pose** sur un lieu remarquable ni sur un gisement (`craftCtx`). Le front retire aussi le décor des
  8 cases autour d'un gisement (sa clairière).
- **Cascade** : son dessin suit la falaise (3 paliers × `HS`). Elle reste à l'échelle 1 (`fixed: true`) ; les autres
  lieux sont agrandis (×1,35).
- **Toute nouvelle source de coffre** doit être ajoutée à `openedOf`, `chestsView.pending`, `openChest`,
  `grantSource`, à la regex de la route `/world/chest` et à `sourceText` (front).
- **Les créations de climat** ont `tier: 'climat'`, toujours ouvert : ce sont les trouvailles qui les gardent. Leur
  règle de pose porte `climate` et `ground`.
- **Prix des annexes** : `annexes.priceOf` renvoie maintenant `{ cost, coins, finds }`. Le front passe ressources
  et trouvailles ensemble (`stockAll`) à `AnnexPanel`, `annexReady` et `CraftBench`.
- **Après un changement du décor** (`propsKey`), `terrain.restand()` refait les carrés cuits. Après un changement
  de brume (quartier acheté), `terrain.invalidate()` refait les cases touchées.
- **Session cloud** : Postgres et les serveurs locaux peuvent s'arrêter (ECONNREFUSED). Relancer
  `service postgresql start`.

## 9. PWA ou vraie app ? (résumé de la discussion)

- **Emballer la même base** (Capacitor, ou Tauri 2 en mobile) apporte les stores, des notifications fiables et les
  achats intégrés. **Pas de fluidité en plus** : la WebView utilise le même moteur que le navigateur.
- **Réécrire en natif ou dans un moteur de jeu** (Godot, Unity, Flutter) coûte des mois de travail et la conversion
  de centaines de dessins générés. Non recommandé.
- **Rester sur le web et passer l'île en WebGL** si nécessaire : c'est le vrai levier de fluidité, utile à la PWA
  comme à une future app.
- **Décision** : une seule base web ; d'abord la mesure sur téléphone et le lot « santé », WebGL si besoin,
  Capacitor plus tard.
